# はじめに

npmサプライチェーン攻撃とは、JavaScriptのパッケージ管理ツールである**npmのエコシステム**を悪用し、正規のパッケージに悪意のあるコードを紛れ込ませる手法です。 開発者のローカルマシンやCI/CD環境が乗っ取られるだけでなく、最終的には**本番アプリを利用するエンドユーザーにまで被害が及ぶ**ため、極めて危険な脅威となっています。

# 要約

- **スクリプト対策（開発者の保護）:** パッケージのインストール時スクリプトを自動実行させない。**→** `pnpm`を使う
- **ゼロデイ対策（ユーザーの保護）:** 公開直後のパッケージにはマルウェアが潜むリスクがあるため、リリースから7日間はインストールしない。**→** `.npmrc` で `min-release-age=7` を設定する

# npmエコシステムと弱点

冒頭でnpmのエコシステムが悪用されていると書きましたが、そこを整理します。

npmでは、

- 誰でも無審査でパッケージを公開できる
- インストール時(`npm i`)にスクリプトが自動実行される

という特徴があります。

npmレジストリは人間による事前審査がないため、誰もが自由にコードを共有でき、結果として世界最大のパッケージ群へと発展しました。

さらに、`package.json` の `scripts`（`preinstall` や `postinstall`など）にセットアップコマンドを定義することで、ネイティブコードのコンパイルやバイナリのダウンロードが自動化されます。開発者は面倒な手動セットアップなしで、コマンド一つ(`npm i`)で簡単にパッケージを使い始めることができます。

しかし、この利便性が、そのまま致命的な弱点に直結しています。 攻撃者にとっても「マルウェアを容易に公開でき、開発者にインストールさせるだけで任意の悪意あるコマンドを全自動で実行できる」仕組みだからです。npmを成功に導いた最大の強みこそが、現在のサプライチェーン攻撃の最大の温床となっています。

では、具体的にはどのようにして悪意のあるコードを仕込むのかというと、以下の３パターンがあるようです。

1.  偽装
2.  乗っ取り
3.  内部犯

偽装では、例えば有名なパッケージと「1〜2文字違い」の名前でマルウェアを公開し、開発者の打ち間違いを待ち伏せます。

乗っ取りは、npm管理画面のログイン情報を何らかの方法で探り当て、文字通りアカウントを乗っ取る方法です。

内部犯も、文字通りですね。パッケージ開発者に正当なメンテナーを装って接近し、マルウェアを仕込むパターンもあるようです。

# 誰が狙われるのか？

こうした手口で混入したマルウェアは、どこで牙を剥くのでしょうか。

攻撃の標的は大きく2つのパターンに分かれます。

#### パターン1: アプリ/エンドユーザを狙う手法

`npm i`やビルドの時点ではファイルをダウンロードするだけで無害だが、アプリケーションとして起動して`require()`や`import`でそのパッケージを読み込んだ際に、悪意のあるコードが発火するタイプの攻撃です。

#### パターン2: 開発者環境を狙う手法

`package.json`のスクリプトに攻撃が仕込まれ、`npm i`を叩いた瞬間にシェルコマンドが発火し開発者マシンに対して攻撃を仕掛ける手法です。

# 具体的な対策: pnpmと.npmrc

以上の構造から、

- パッケージを無条件に信用しない (ゼロトラスト)
- パッケージのスクリプトを自動実行しない
- 既知の脆弱性を弾く

の3点が対策の原則となります。

これら原則を守りつつ、開発体験を損なわないためのアプローチが、**.npmrcの設定**と**pnpmの導入、auditによるチェック**です。

## 1\. ゼロデイ攻撃を防ぐ(.**npmrcの設定**)

悪意のあるコードが含まれたパッケージ(またはアップデート)が公開された直後の未知の脅威(ゼロデイ攻撃)を防ぐ対策です。

プロジェクトの直下に `.npmrc` ファイルを作成し、以下の1行を記述します。

```
min-release-age=7
```

この設定により、リリースされてから7日未満のパッケージはインストールされなくなります。

悪意のあるパッケージの多くは、公開後数日以内にセキュリティコミュニティによって発見されレジストリから削除されるので、ゼロデイを防げます。

## 2\. pnpmの導入

pnpm(v9以降)はセキュリティ設計が非常に優れており、**明示的に許可されていないパッケージのスクリプトは実行しない**という挙動がデフォルトになっています。

パッケージにスクリプトが定義されていれば、一律でブロックして「スキップしました」と警告を出します。

インストールにスクリプトが必須のパッケージの場合は、以下のように`package.json` の `pnpm.onlyBuiltDependencies`(許可リスト)に対象を追記することでスクリプト実行可能です。

```
{
  ...,
  "pnpm": {
    "onlyBuiltDependencies": [
      "パッケージ名"
    ]
  }
}
```

# 3\. auditによるセキュリティ監査

ゼロデイ攻撃だけでなく、既知の脆弱性(CVE)が本番環境に紛れ込むのを防ぐため、ビルド前に強制的なセキュリティ監査(audit)を組み込みます。

具体的には、`package.json` のビルドスクリプトの手前で `pnpm audit --audit-level=high`などのコマンドを走らせるよう設定します。

これにより、重大度が高(High)以上の脆弱性が見つかった場合は強制的にビルドが失敗させます。

例えば、Next.jsを例に以下のように組み込みます。

```
{
  ...,
  "scripts": {
    "dev": "next dev",
    "audit:ci": "pnpm audit --audit-level=high", # audit実行
    "build": "pnpm run audit:ci && next build", # audit実行
  }
}
```

**⚠️**`audit` コマンドは万能ではない

`audit`は、報告された既知の脆弱性と手元のパッケージを照合する仕組みなので、昨日公開されたばかりのマルウェアや、乗っ取りによる巧妙な未知の攻撃（ゼロデイ攻撃）は、データベースに登録されるまで完全にすり抜けてしまいます。ですのでauditが通ったから絶対大丈夫ということはないのを留意しておく必要があります。

## 補足: npmからpnpmへの移行ステップ

既存のプロジェクトを`pnpm`に移行するのは非常に簡単です。

以下の4ステップで完了します。

**ステップ1: pnpmの有効化**

Node.jsに標準搭載されている`Corepack`を使ってpnpmを有効化します(別途インストールは不要)。

```
corepack enable
corepack prepare pnpm@latest --activate
```

**ステップ2: 既存のnpmファイルの削除**

古い依存関係とロックファイルを削除し、環境をクリーンにします。

```
rm -rf node_modules package-lock.json
```

**ステップ3: pnpmでインストール**

新しくインストールを実行し、pnpm用のロックファイル（`pnpm-lock.yaml`）を生成します。

```
pnpm install
```

**ステップ4: package.json のアップデート**

チーム全員が`pnpm`を使うように強制する設定と、スクリプト実行ブロックの設定を追記します。

```
{
  "packageManager": "pnpm@9.x.x",
  "scripts": {
    "preinstall": "npx only-allow pnpm"
  },
  "pnpm": {
    "onlyBuiltDependencies": []
  }
}
```

以後は `npm run build` などを `pnpm run build` に置き換えて開発を進めます。

# サプライチェーン攻撃を受けやすい言語

npmは便利さの裏返しの構造的弱点がありますが、npmと同様の弱点を持つ言語、パッケージマネージャを調べてみました。

### グループ1: npmと同じ構造を持つ言語⚠️

これらの言語のパッケージマネージャも、npmと同様に「誰でも無審査で公開できる」「インストール（またはビルド）時に任意のコードが自動実行される」という特徴を持っており、頻繁にサプライチェーン攻撃の標的になっています。

- **Python (PyPI / pip)**
  - npmに次いで攻撃のターゲットにされやすいエコシステムです。ソースコード形式で配布されるパッケージをインストールする際、`setup.py` というセットアップ用ファイルが自動実行されます。この中に悪意のあるPythonコードを仕込んでおくことで、開発者のPCからDiscordの認証トークンや環境変数を盗み出す事件が報告されています。
- **Ruby (RubyGems)**
  - こちらも誰でも簡単にパッケージ（Gem）を公開できます。C言語などのネイティブ拡張機能をビルドするための仕組みとして、インストール時に `extconf.rb` などのRubyスクリプトが自動実行される仕様があり、ここがマルウェアの侵入経路として悪用されます。
- **Rust (Cargo / crates.io)**
  - パッケージ（Crate）の公開は無審査です。また、プロジェクトのビルド時に `build.rs` というビルドスクリプトが開発者のローカル環境で自動的にコンパイル・実行される仕様になっており、これを悪用してマルウェアを感染させるタイポスクワッティング事件が実際に報告されています。

### グループ2: 公開ハードルが高く偽装が難しい言語✅

前述のグループ1とは対照的に、以下の言語のエコシステムは「パッケージ公開時の身元証明が厳しい」「インストール時の自動実行フックを持たない」といった構造になっており、サプライチェーン攻撃のリスクが低く抑えられています。

- **Java (Maven Central / Gradle)**
  - パッケージを公開する際、名前空間に対する**ドメイン所有権の証明**を厳格に求めています。例えば `org.apache.commons` という名前で公開できるのは、実際に `apache.org` のドメインを持っている組織だけです。これにより、偽名を使ったタイポスクワッティングが構造的に不可能です。また、依存関係をダウンロードしただけで任意のスクリプトが発火する仕組みもありません。
- **Go (Go Modules)**
  - Goのパッケージ管理は、npmのような中央集権的なレジストリではなく、`[github.com/user/repo](https://github.com/user/repo)` のように**ソースコードのホスティングURLそのものをパッケージ名として指定**する分散型の仕組みを採用しています。そのため名前を似せて騙すこと(タイポスクワッティング)が難しくなっています。また、`go get` などのコマンドはソースコードをダウンロードしてコンパイルするだけで、任意のインストールスクリプトを実行する機能は持っていません。
- **Swift (Swift Package Manager)**
  - Goと同様に、GitリポジトリのURLを直接指定して依存関係を解決します。パッケージフェッチ時のシェルスクリプトを自動実行するような仕組みも存在しません。
- **.NET (NuGet)**

  - NuGetには**ID プレフィックスの予約(Prefix Reservation)**という仕組みがあります。Microsoftなどの公式組織が特定のプレフィックス（例: `Microsoft.*` や `System.*`）を予約しており、第三者がその名前を騙ってパッケージを公開できないようになっています。また、過去にはインストール時にスクリプト（`install.ps1`）を自動実行する機能がありましたが、セキュリティ上の理由などから現代の形式（`PackageReference`）では廃止・無効化されており、安全性が高まっています。

# おわりに

npmパッケージの公開やインストールの手軽さは、JavaScript, Node.jsによる開発を爆発的に進化させました。しかし現在は、その利便性が攻撃者に悪用されています。

対策として、本記事で紹介した`pnpm`や`.npmrc`の設定による**ゼロトラストを前提とした仕組みによる防御**が、標準となっていくかと思います。
