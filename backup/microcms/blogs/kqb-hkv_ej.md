# はじめに

2026年10月20日、インドの認証局eMudhra(イー・ムドラ)の中間証明書8件において、秘密鍵が第三者でも数ミリ秒で復元可能な状態にあることがわかりました。

なんと中間証明書の秘密鍵が「4」「56」「115」といった暗号鍵とは呼べない極端に小さい数値が使われていたようです。

原因は鍵生成スクリプトの欠陥と人為的ミスとのことですが、事態を重く見たGoogleやMozillaなどによって、大元であるルート証明書の失効という異例の事態にまで発展しています。

今回は、

- 秘密鍵について
- 中間証明書の秘密鍵が再現されるとどうなる？
- 中間証明書・ルート証明書が失効するとどうなる？

について書いていきます。

# 秘密鍵の値はどのように決まるのか

今回使われていた「**P-384(楕円曲線暗号: ECC)**」という暗号方式において、適切に生成されたP-384の秘密鍵は「1から2の384乗までの範囲からランダムに選ばれた1つの整数」になります。

384bitとは、10の115乗以上という天文学的な数の組み合わせになるので、現代のコンピュータでは推測不可能な値です。

実際にP-384による秘密鍵を生成してみました。

#### p-384の鍵(EC鍵)

```
$ openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-384 -out private.key

$ ls
private.key
```

private.keyができました。

ファイル中身を見てみます

```
$ cat private.key
```

# 秘密鍵を再現する方法

公開鍵暗号(楕円曲線暗号)では、公開鍵と秘密鍵は数学的な計算で結びついています。

公開鍵は「**あらかじめ決められた基準点(G)**に対して、秘密鍵の数値の回数だけ足し算（または掛け算）を繰り返す」ことで作られます。

本来、天文学的な大きさの秘密鍵が使われていれば、公開鍵から秘密鍵を逆算して割り出すことは現代のコンピュータでも不可能です。

しかし、今回のように秘密鍵が「4」だった場合はどうでしょうか。

中間証明書には「中間CAの公開鍵」が必ず含まれているため、誰でも公開鍵を手に入れることができます。

攻撃者はその公開鍵を見ながら、手元のPCで次のような総当たり計算を行うだけです。

1.  「秘密鍵が1だとしたら、公開鍵はどうなる？」 → 実際の公開鍵と不一致
2.  「秘密鍵が2だとしたら？」 → 不一致
3.  「秘密鍵が3だとしたら？」 → 不一致
4.  「秘密鍵が4だとしたら？」 → 実際の公開鍵と一致！秘密鍵は「4」だと確定

このような総当たりでも数m秒で秘密鍵を当てられたと思われます。

例えば以下のようなコードで秘密鍵を探し出します。

```
from ecdsa import NIST384p

# 楕円曲線の基準点Gを取得 基準点は公開情報
G = NIST384p.generator

# 中間証明書の公開鍵
target_pubkey = xxx

# 1から順に総当たりで試す（今回は1000まで）
for i in range(1, 1000):
    # 「もし秘密鍵が i だったら？」と仮定して公開鍵を計算
    guess_pubkey = i * G

    # 計算した公開鍵が、ターゲットの公開鍵と一致するかチェック
    if guess_pubkey == target_pubkey:
        print(f"実際の公開鍵と一致！秘密鍵は: {i} です")
        break
```

# 中間証明書の秘密鍵が再現されるとどうなる？

[前回の記事](https://tokiolab.dev/blog/o0194v13ov9u/)で「中間CAの秘密鍵はサーバ証明書を発行(署名)するために使われる」と解説しました。

```text
┌──────────────────────────┐
│ 中間CA
│
│ 持っているもの
│ ・中間CA秘密鍵
│ ・中間CA公開鍵
└──────────────────────────┘
             │
             │ 中間CA秘密鍵で
             │ サーバ証明書に署名
             ▼
┌──────────────────────────┐
│ example.comのサーバ証明書
│
│ ・example.com
│ ・サーバ公開鍵
│ ・有効期間
│ ・中間CAによる署名
└──────────────────────────┘
```

発行されたサーバ証明書は、**証明書チェーン**という仕組みで「正規の認証局により発行されてるね」とわかります。

#### 証明書チェーン

1.  ハンドシェイクにおいて、クライアントがサーバ証明書と中間証明書を取得
2.  中間証明書の公開鍵で、サーバ証明書の署名を検証
3.  自分が持っている(Trust Store)ルート証明書の公開鍵で、中間証明書の署名を検証

このように、署名を検証することで確認できます。

ですので、秘密鍵が攻撃者に再現されると任意のドメインの偽のサーバ証明書が発行できてしまうことになります。

そして、その秘密鍵は正しいものなので証明書チェーンで検証成功するので、正しい証明書と攻撃者の証明書が区別できなくなります。

```text
┌──────────────────────────┐
│ 攻撃者
│
│ 持っているもの
│ ・再現した中間CA秘密鍵
│ ・中間CA公開鍵(中間証明書から取得できる)
└──────────────────────────┘
             │
             │ 中間CA秘密鍵で
             │ サーバ証明書に署名
             ▼
┌──────────────────────────┐
│ example.comの偽サーバ証明書
│
│ ・example.com
│ ・サーバ公開鍵
│ ・有効期間
│ ・攻撃者による署名
└──────────────────────────┘
```

#### 考えられる攻撃

もし、偽サーバ証明書のサーバに使い繋いでしまうと、

- HTTPS通信の盗聴および改ざん

のリスクにされされます。

# 中間証明書・ルート証明書が失効するとどうなる？

今回の件で、中間証明書・ルート証明書が失効になります。

これはどのような影響があるのでしょうか？

## 1\. 中間証明書だけ失効した場合

中間証明書だけを失効リストに入れた場合、アクセスする経路によって異なります。

### **ブラウザへの影響: ✅安全**

Chrome、Firefox、Safariなどのモダンブラウザは、ベンダー独自の失効リスト(CRLSetsなど)の自動更新や、CT(証明書の透明性)ログの確認を標準で行っています。

ブラウザ本体の手動アップデート等をしなくても裏側で安全が保たれます。

- **挙動:** 画面に「NET::ERR\_CERT\_REVOKED」といった真っ赤な警告画面が表示され、通信は強制的に遮断されます（情報漏洩は防げます）。

### **プログラム(curl, Python, Goなど)への影響: 🚨危険**

これが今回の事件で**最も警戒されるパターン**です。

多くの標準的なプログラムは、デフォルトでは証明書の失効リスト(CRLやOCSP)を確認しに行きません。

- **挙動:** プログラムは失効している中間証明書を信用し、エラーを出さずに普通に接続を完了してしまいます。もし接続先が攻撃者の偽サーバーだった場合、認証トークンや個人情報をそのまま送信してしまい、盗聴や改ざんのリスクがあります。

## 2\. ルート証明書も失効した場合

中間証明書の失効だけではプログラム側の情報漏洩を防げないため、今回GoogleやMozillaは「大元のルート証明書ごと削除する」という手段に出ました。

- **どうなるか:** OSのリストからルート証明書が削除されると、ブラウザやプログラムは証明書を信用しないのでエラーになり、強制的に通信を遮断するようになります。
- **結果:** 情報漏洩リスクは完全に防げます。しかし副作用としてその証明書を使っていた自社のAPIなどはダウンタイムが発生する恐れがあります。

## 3\. 取れる対策

上記の通り、ルート証明書がOSから削除されればプログラムの通信も安全に遮断されます。

しかし、**OSによってこのリストが更新されるタイミングが異なります。**

- **一般的なOS(Windows/macOS/iOS等):** Trust Storeをバックグラウンドで自動更新する仕組みがあるため、手動のOSアップデート等は不要で、勝手に安全な状態になります。
- **サーバーOS(Linux / Dockerコンテナ等):** 以下のように自分で証明書リスト（`ca-certificates`）を明示的に更新しない限り、古いルート証明書を信じ続けてしまいます。

**Ubuntu / Debian系の例**

```
sudo apt-get update
sudo apt-get install --only-upgrade ca-certificates
```

**RHEL / AlmaLinux / Amazon Linux系の例**

```
sudo yum update ca-certificates
# または
sudo dnf update ca-certificates
```

**Dockerコンテナの場合**

Dockerfileの中に更新コマンドを組み込んでおき、さらにキャッシュを無効化してリビルドする必要があります。

```
FROM ubuntu:22.04
RUN apt-get update && apt-get install -y --only-upgrade ca-certificates
```

ビルドコマンド

```
$ docker build --no-cache -t my-app:latest .
```

# おわりに

今回は、インドの認証局eMudhraの中間証明書インシデントから、「秘密鍵」の強度の重要とそれが破られたときにシステム全体へどのような影響を及ぼすかを整理しました。

対応としては、サーバーOSやDockerコンテナ内の証明書リスト（`ca-certificates` パッケージなど）を常に最新にアップデートし続けることが大事だと思います。
